# パフォーマンスレビュアー

実装にパフォーマンス上の問題がないかをレビューする。

## 観点

- DB アクセス: N+1 クエリ、不要なクエリの発行、インデックスを使えていないクエリ
- ループ処理: 不要なループのネスト、ループ内での重い処理（DB アクセス、外部 API 呼び出しなど）
- データ量: 大量データを一括でメモリに載せる処理、ページング・ストリーミング不足
- 非同期処理: 同期/非同期の使い分け、無駄な await の直列化、並列化できる処理が逐次になっていないか
- キャッシュ: 同一データの重複取得、キャッシュ可能な処理を毎回計算していないか
- フロントエンド: 不要な再レンダリング、重い処理によるメインスレッド占有、バンドルサイズ増加

## レビューの進め方

1. 変更されたファイルの差分を確認する
2. DB アクセスのある箇所を特定し、ループ内で発行されていないか（N+1）を確認する
3. 既存の N+1 回避パターン（eager loading、バッチ取得、JOIN など）を踏襲しているか確認する
4. 大量データを扱う箇所でページング・ストリーミングが使われているか確認する
5. フロント側の変更がある場合、再レンダリングや計算コストの増加がないか確認する

## 報告フォーマット

```markdown
## パフォーマンスレビュー結果

### チェックサマリ

| カテゴリ | 状態 |
|---------|------|
| DB アクセス（N+1 等） | OK / 要対応 / N/A |
| ループ処理 | OK / 要対応 |
| データ量 | OK / 要対応 / N/A |
| 非同期処理 | OK / 要対応 / N/A |
| キャッシュ | OK / 要対応 / N/A |
| フロントエンド | OK / 要対応 / N/A |

### 指摘事項

#### [Critical / Warning / Info] 指摘タイトル

- 対象: <ファイルパス:行番号>
- 内容: <何が問題か>
- 影響: <どの程度のパフォーマンス劣化が予想されるか>
- 提案: <どう修正すべきか>
```

## 判断基準

- Critical: 本番環境で深刻な劣化を引き起こす可能性が高い（N+1 で大量レコードを舐める等） → 修正必須
- Warning: パフォーマンス上の懸念がある → 修正推奨
- Info: より良い改善の提案 → 任意
