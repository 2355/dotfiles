以下のガイドに従い、$ARGUMENTS の PR の内容をわかりやすく解説した artifact を作成する。

$ARGUMENTS が空、または PR の URL でない場合は、作業を始める前にユーザに PR の URL を尋ねる。

## ガイド

- 初めに3行程度の短いまとめ
- 背景知識のない人が読んでも理解できる内容
- how ではなく what を中心に説明する
- 必要に応じて図解を交える
- レビューの起点、ファイルの読み方

読み手は「この PR をこれからレビューする人」または「変更内容を把握したい人」で、リポジトリやドメインの前提知識を持っていないことを想定する。ページを読み終えた時点で「何が変わるのか」「なぜ変えるのか」「どこから読めばよいか」がわかる状態を目指す。

## 手順

### 1. PR の情報を集める

`gh` で PR の本文・差分・関連情報を取得する。

```bash
gh pr view <url> --json title,body,author,baseRefName,headRefName,files,additions,deletions,baseRefOid,headRefOid,closingIssuesReferences,labels
gh pr diff <url>
```

- 差分が巨大な場合は、まず `gh pr diff <url> --name-only` で全体像を掴み、lockfile や生成物を除いた主要なファイルを読む。`gh pr diff --exclude` は除外対象外のファイルまで出力から消えることがあるため使わず、全差分を取ってからファイル単位で絞る
- 行数を載せる場合は `files` の `additions` / `deletions` の値をそのまま使う。暗算で合算すると誤りやすい
- 背景（なぜこの変更が必要か）を知るために、PR 本文から参照されている資料を読む。URL だけでなく Jira のチケットキーなど、キーだけの参照も辿る。深さは「なぜ変えるのか」「どういう仕様か」の根拠が得られるまでを目安とし、チケットから参照された設計 doc までは読んでよい。使える MCP やコマンドで読めないものは、読めなかったとページに書く
- 差分だけで意味が取れない箇所は周辺コードを読む。読む commit は `baseRefOid`（変更前）/ `headRefOid`（変更後）に固定する。ローカルのチェックアウトが別の commit を指していると、変更前後を取り違えた解説になるため
  - ローカルにリポジトリがあれば `git show <oid>:<path>` で読む（手元に commit がなければ `git fetch origin <oid>`）
  - なければ `gh api 'repos/{owner}/{repo}/contents/{path}?ref=<oid>' -H 'Accept: application/vnd.github.raw'` で取得する

解説に書く仕様・挙動は、差分・PR 本文・周辺コードなど読んだものを根拠にする。推測で補った部分は推測だとわかるように書く。読み手はこのページを信じてレビューするので、もっともらしい推測が事実のように書かれていると、レビューの見落としにつながる。

### 2. 内容を組み立てる

以下の構成を基本とする。1（まとめ）と 4（レビューの起点とファイルの読み方）は必ず入れる。それ以外は PR の性質に応じて増減・統合してよい。

1. **まとめ（3行程度）** — 何を・なぜ変えるのかを、この節だけ読めば伝わるように書く
2. **背景** — 変更前はどうなっていて、何が問題だったのか。ドメイン用語やリポジトリ固有の概念はここで短く説明する
3. **何が変わるのか** — 変更後の振る舞い・データ・画面・API などを what の粒度で説明する。コードの書き方（how）ではなく、システムとして何ができるようになる／何が変わるのかを書く
4. **レビューの起点とファイルの読み方** — どのファイルから読み始めるとよいか、推奨する読む順番とその理由、ファイルごとの役割（中心的な変更／それに追従しただけの変更／テスト／生成物など）。重点的に見てほしい箇所や、判断が分かれそうな設計上のポイントがあれば挙げる

図解は独立した節にせず、理解を助ける節の中に置く。変更前後の比較、データフロー、処理の流れ、コンポーネントの関係など、文章より図のほうが早く伝わるものがあれば描く。図が理解を助けない PR では無理に入れない。

what を中心にする理由：レビュアーはコードそのものは差分で読める。ページの価値は、コードを読む前に「この変更が何を達成しようとしているか」の地図を渡すことにある。how の説明は、読み方の案内に必要な範囲に留める。

### 3. artifact を作成して公開する

HTML ページの artifact として作成・公開する。Claude Docs などの文書 connector は使わない。図を自由に描けるページ形式のほうが、この用途に向いているため。

- 最初に Artifact ツールを `action: "quickstart"`、`intent: "other"` で呼び、その結果のページデザインの指示に従う。形式は HTML ページと決まっているので、Artifact type や design system の一覧取得は不要
- 図を描く場合は `artifact-diagramming` スキルも読み込む
- ページは日本語で書く
- ファイルパスや関数名などのコード識別子は原文のまま書く
- ファイル名には GitHub の該当ファイルへのリンクを付けると、読み手がそのままコードに飛べる。リンクは `headRefOid` を使った permalink（`https://github.com/{owner}/{repo}/blob/<headRefOid>/<path>`）にする。ブランチ名で作ると、マージしてブランチが消えた後に切れるため

公開後、ユーザには artifact のリンクと、まとめの3行を返す。
