name: create-pr
description: PR を作成する。現在のブランチから base ブランチ（ユーザに選択させる）に向けて PR を作成し、PR テンプレートをベースに概要欄を記入する。ユーザが「PR作って」「プルリク作成して」「PR出して」などと言った場合や、Issue 番号を指定して PR 作成を依頼された場合にこのスキルを使用する。
argument-hint: "[issue-url or issue-number] [--draft]"
---

$ARGUMENTS を元に、現在のブランチから PR を作成する。`--draft` が含まれる場合のみ draft PR にする。

## 手順

1. **前提を確認する**
   - `gh repo view --json defaultBranchRef -q '.defaultBranchRef.name'` でデフォルトブランチを取得する
   - 現在ブランチがデフォルトブランチと同じならエラーで終了する
   - 現在ブランチがリモートに無い、あるいはローカルが先行している場合は `git push -u origin HEAD` で push する

2. **base ブランチをユーザに確認する**
   - `gh pr list --state all --limit 50 --json baseRefName -q '.[].baseRefName' | sort | uniq -c | sort -rn` で過去 PR の base ブランチを使用頻度順に取得する
   - 候補リストはデフォルトブランチを先頭に置き、続けて過去 PR の base を頻度順に並べる。デフォルトブランチは頻度リスト側から除いて重複させない
   - 候補が 4 つ以内なら全部、5 つ以上なら上位 3 つ + 「Other」（手入力）を AskUserQuestion で提示する。デフォルトブランチには「(Recommended)」を付ける
   - 過去 PR が無い場合はデフォルトブランチのみを提示する
   - ユーザが選択した branch を以降の手順で base として使う

3. **PR テンプレートを取得する**
   - `.github/PULL_REQUEST_TEMPLATE.md` を Read ツールで読む
   - 無ければ「概要 / 関連 Issue」の最低限の枠組みを自分で組む

4. **PR タイトルを決める**
   - `$ARGUMENTS` から `--draft` フラグを除いた値を Issue 指定として解釈する
   - Issue 指定あり: `gh issue view <issue>` で取得した Issue タイトルをそのまま使う
   - Issue 指定なし: `git log <base-branch>..HEAD` のコミット内容からタイトルを生成する

5. **差分を読む**
   - `git diff --stat <base-branch>...HEAD` と `git diff <base-branch>...HEAD` を見る

6. **PR 本文を下書きする**
   - 後述「本文の指針」の型に従ってテンプレートのセクションを埋め、提出前チェックまで通す
   - Issue 指定あれば Issues 欄に Issue URL を記入する

7. **補足 artifact が必要か判定する**
   - 後述「補足 artifact」の条件で判定する。判定は下書きが出来上がってから行う

8. **必要と判定した場合のみ、artifact を作って本文にリンクする**
   - 後述「補足 artifact」に従って作成し、下書きの先頭に 1 行でリンクを追加する

9. **PR を作成する**
   - `gh pr create --base <base-branch>` で PR を作成する。`$ARGUMENTS` に `--draft` が含まれていた場合のみ `--draft` を付ける
   - 作成後、PR の URL をユーザに報告する
   - artifact を作った場合は、後述「共有設定はユーザにしかできない」に従って報告する

## 本文の指針

### 読者

読者は **この PR のページしか開いていない人**。ローカルのセッション、あなたとユーザの会話、途中の試行錯誤を一切知らない。その人が本文を 30 秒読んで「何が変わり、なぜ必要で、どこに影響するか」を言えれば成功。

### 本文の型

テンプレートのセクションに、次の 4 要素だけを流し込む。

| 要素 | 中身 | 書き方 | 省略 |
|---|---|---|---|
| 結果 | マージ後に何が成立しているか | 現在形の状態で書く。「〜できる」「〜が〜になる」 | 不可 |
| 理由 | 解決した問題 / 満たした要件 | Issue があれば URL のみ。Issue に書いてあることを本文で繰り返さない | 不可 |
| 設計判断 | 「採った案 / 捨てた案 / 理由」 | 1 判断 1 行、最大 3 件 | 下記の判定で 0 件なら要素ごと省く |
| 影響 | 挙動が変わる利用側 / 移行手順 / 後方互換性 | 該当が無ければ「なし」の 1 行 | 不可 |

**設計判断に書くのは次の 2 つだけ。** どちらも無ければ 0 件として要素を省く。

- 実装中に別案を検討して却下した箇所
- 既存コードの慣習・パターンから意図的に外れた箇所

「変数名をこうした」「この順序で呼んだ」のような実装の細部は設計判断ではない。3 件を超える場合は、書ききれない分は本文に足さず「補足 artifact」に回す。

### 長さ

- **1 行 = markdown の 1 行**。箇条書きの 1 項目、表の 1 行を 1 行として数える。見出しと空行は数えない
- 各要素は 3 行以内
- 記述部分の合計は 30 行以内。artifact リンクを貼る場合は 15 行以内
- テンプレートのチェックリストは行数に数えない

### 文の書き方

- 主語はコード / システム / 機能。人（自分・ユーザ・レビュアー）を主語にしない
- 完了した結果の状態を書く。到達までの経過は書かない
- ファイル名・関数名・クラス名を列挙しない。diff とレビュー画面が既に持っている情報

### 提出前チェック

下書きを 1 行ずつ見て、次に当てはまる行を削除する。削除して短くなった分を埋めるために書き足さない。

| 下書きの特徴 | 例 | 措置 |
|---|---|---|
| 手順・経過を語っている | 「まず〜を追加し、次に〜を修正した」 | 削除し、結果の状態だけ残す |
| セッション文脈が漏れている | 「相談の結果」「指摘を受けて」「当初の実装では」 | 削除 |
| 開発プロセスの報告 | 「TDD で実装した」「テストを追加して全て通した」 | 削除。CI が示す |
| ファイル / 関数の列挙 | 「`foo.ts` の `bar()` を〜に変更」 | 削除。diff が示す |
| Before / After のコード引用 | 変更前後のコードブロック | 削除。diff が示す |
| 一般論・自明な効能 | 「保守性が向上します」「型安全になります」 | 削除、または具体的な結果に置き換える |
| この差分に無いことの言及 | 「今後は〜する予定」 | 削除。Issue に書く |

### 「レビューしてほしい観点」セクションがある場合

残すのは、人間の判断 / 経験が必要な事項だけ。grep / Read で確定できることは本文を書く前に自分で調査し、確認済みの事実として記載する。残った設計判断やトレードオフを観点に書く。

## 補足 artifact

### 作る条件

**本文の下書きが完成してから判定する。** 次のどちらかに当てはまる場合だけ作る。

- **本文の型に収まらない**: 提出前チェックを通した下書きが、次のいずれかの状態にある
  - 記述部分が 30 行を超えている
  - 「結果」「理由」が、diff に現れない前提（この PR で導入した概念・用語、変更したデータモデル、跨いだコンポーネント間のフロー、追従した外部仕様）に触れずには 3 行で書けない
  - 設計判断が 4 件以上ある
- **実質変更行数が 500 行超、または実質変更ファイル数が 20 超**: `git diff --stat <base-branch>...HEAD` の数値から、lockfile・自動生成ファイル・リネームのみのファイル・フォーマット差分のみのファイルを除いて数える

上記に当てはまらないなら作らない。「あった方が親切だから」で作らない。

### 中身

Artifact を書く前に `artifact-design` skill を読む。図を描くなら `artifact-diagramming` skill も読む。

節は上から順に置く。該当する内容が無い節は飛ばす。

1. **背景** — この変更が必要になった状況。PR を見た人が知らない前提から始める
2. **変更前の構造と課題** — 図 + どこが問題かの指摘。構造が変わらない変更（設定値の一括更新、機械的な置換など）ではこの節と次の節を飛ばし、代わりに「変更の内訳」を表で示す
3. **変更後の構造** — 図。変更前の図と同じ記法・同じ要素配置にして、差分が目で読めるようにする
4. **設計判断** — 採った案 / 捨てた案 / 理由
5. **レビューの入口** — artifact の各節と PR の該当ファイルの対応

図は「文章だと読み返しが必要になるもの」に使う（構造の変更前後、データフロー、状態遷移）。列挙で足りるものは表にする。図を無理に作らない。

artifact 側も読者は同じ「PR しか見ていない人」。手続き的な経過やセッション文脈を書かないルールは本文と同じ。

### PR 本文へのリンク

本文の先頭に 1 行だけ置く。

```
> 背景と設計の詳細: <artifact URL>
```

artifact を作っても、本文の 4 要素（結果 / 理由 / 設計判断 / 影響）は省略しない。artifact を開かなくても概要は分かる状態を保つ。

### 共有設定はユーザにしかできない

Artifact は既定で非公開で、公開範囲を変える手段は agent 側に無い。共有設定をしない限り、PR に貼った URL はレビュアーには開けないリンクのままになる。

PR 作成後の報告に、次の 2 つを必ず含める。

- artifact の URL と、共有設定が必要であること
- 共有しない選択をする場合は、PR 本文のリンク行を削除する必要があること
