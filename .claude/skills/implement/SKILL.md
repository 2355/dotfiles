$ARGUMENTS で指定されたファイルを起点に、plan の生成・実行を行う。

## 引数の解析

- 第1引数: spec.md または plan.md のパス
  - ファイルの内容を読んで spec か plan かを判断する
  - spec の場合 → Phase 0（plan 生成）から開始
  - plan の場合 → Phase 1（plan 実行）から開始
  - 省略された場合、直近の会話コンテキストから推測する
  - 推測できない場合はユーザに確認する
- plan.md のパスから共通IDを抽出する（例: `.claude/123/plan.md` → `123`）

## サブエージェント

以下のカスタムエージェントを Agent ツールの `subagent_type` で指定して起動する:

| subagent_type | 役割 |
|---------------|------|
| `implement-coder` | コーディングタスクの実行（テストコードの作成も必須） |
| `implement-reviewer-functional` | 機能観点のレビュー |
| `implement-reviewer-architecture` | アーキテクチャ観点のレビュー |
| `implement-reviewer-security` | セキュリティ観点のレビュー |
| `implement-reviewer-performance` | パフォーマンス観点のレビュー（N+1 等） |
| `implement-qa-tester` | ブラウザでの動作確認 |

オーケストレーターの役割はこのスキルを実行するエージェント自身が担う（`references/orchestrator.md` を参照）。

## Phase 0: plan 生成

spec.md を起点に、実行計画（plan.md）を生成する。

### 0-1. spec の読み込みと理解

spec.md を読み、以下を把握する:

- 背景とゴール
- 要件リスト
- 受け入れ条件
- 技術的な補足（対象ファイル、影響範囲）
- 未解決の疑問点

未解決の疑問点がある場合は、plan 作成前にユーザに確認する。
疑問が解消されないまま plan を作ると、手戻りの原因になる。

### 0-2. コードベース調査

spec の内容をもとに、実装に必要な情報を収集する。

- 変更対象のファイルを特定する
- 既存の実装パターン・規約を把握する（テストの書き方、コンポーネント構成、API の設計パターンなど）
- 依存関係やインポート構造を確認する
- 影響を受ける可能性のある既存機能を洗い出す

調査結果は plan.md の「技術コンテキスト」セクションに反映する。

### 0-3. タスク分解

要件をタスクに分解する際の方針:

- 各タスクは「1つのサブエージェントが独立して完了できる粒度」にする
- タスク間の依存関係を明示する（どのタスクが終わらないと次に進めないか）
- 並列実行可能なタスクを特定する
- 各タスクに対して、変更対象ファイルと期待する変更内容を具体的に記載する

タスク分解が適切かどうかの判断基準:
- 1 タスクが複数ファイルの大規模な変更を含む → 分割を検討
- 2 つのタスクが同じファイルの同じ箇所を変更する → 統合を検討
- タスクの説明が曖昧で「何をすれば完了か」が不明確 → 具体化する

### 0-4. plan.md の生成

`references/plan-template.md` のフォーマットに従って plan.md を出力する。
テンプレートの各セクションを、spec とコードベース調査の結果で埋める。

出力先: spec.md と同じディレクトリに `plan.md` として保存する。

### 0-5. ユーザ確認

生成した plan.md の内容をユーザに提示し、以下を確認する:

- タスク分解の粒度は適切か
- 依存関係の認識に誤りはないか
- レビュー観点に過不足はないか
- QA シナリオは十分か

ユーザが承認するまで plan.md を修正する。
**ユーザの承認を得てから Phase 1 に進む。承認なしに実行を開始しない。**

## Phase 1〜5: plan 実行

plan.md の「オーケストレーション指示」セクションに従い、Phase 1〜5 を順番に実行する。
オーケストレーターの役割はこのスキルを実行するエージェント自身が担う。

### 作業環境の構築

Phase 1 開始前に、以下のコマンドを順番に実行する。各ステップでエラーが発生した場合はユーザに報告して指示を仰ぐ。

#### worktree を作成

```bash
wtp add -b feature_$(whoami)_<共通ID>
```

出力から worktree のパスを取得する。`📁 Location:` の行に表示されるパスを使う。

出力例:

```
✅ Worktree created successfully!
📁 Location: /Users/user1/work/worktrees/feature_user1_123
🌿 Branch: feature_user1_123
```

#### worktree ディレクトリへ移動

```bash
cd <取得したパス>
```

#### worktree 環境のセットアップ

```bash
scripts/worktree-up.sh
```

**エラー時の対応:**

- `wtp add` が失敗した場合（ブランチ名の重複など）→ ユーザに報告し、対応を確認する
- `scripts/worktree-up.sh` が失敗した場合 → エラー内容をユーザに報告し、続行するか確認する
- ユーザのアクションが必要な場合（認証、手動操作など）→ 何が必要かを明示してユーザを呼び出す

### plan の実行

plan.md には以下が記載されている。必ず plan.md を読んでから実行に移ること。

- 各 Phase の内容と完了条件
- タスクの依存関係と並列実行グループ
- コーダー・レビュアー・QA テスターへのプロンプト
- レビューループの仕組みとラウンド数
- 実行フロー図
- エスカレーション条件

#### サブエージェントの起動

Agent ツールで `subagent_type` を指定して起動する。各エージェントには plan.md に記載されたプロンプトを渡す。

### 完了報告

ユーザに以下を報告する:

- 完了したタスクの一覧
- レビューラウンド数と最終結果
- QA の結果
- 次のステップの提案（`create-pr` スキルで PR 作成など）

## 注意事項

### plan 生成時

- plan.md に推測を含めない。コードベース調査で確認できた事実のみを記載する
- タスクの粒度が大きすぎると並列化の恩恵が減り、小さすぎるとオーバーヘッドが増える。1タスク = 1つの明確な変更単位を目安にする
- レビュアーのプロンプトには、そのプロジェクト固有の規約（CLAUDE.md の内容など）も含める
- QA テストシナリオは受け入れ条件を網羅しつつ、リグレッションの確認も含める

### plan 実行時

- plan.md の指示に従う。plan に書かれていない作業を勝手に追加しない
- サブエージェントには十分なコンテキストを渡す（タスクの背景、変更対象、完了条件）
- worktree 環境で作業するため、元のブランチには影響しない
- 作業中に plan の内容と実際のコードベースに齟齬が見つかった場合は、ユーザに確認する
