```markdown
## 実行フェーズ

### Phase 1: コーディング

各タスクをコーダーサブエージェントに割り当てて実行する。
並列グループが同じタスクは同時に実行する。依存があるタスクは、依存先の完了を待ってから開始する。
  ```

  ```
### Phase 2: レビュー

コーディング完了後、4 つの観点でレビューを並列実行する。
レビューは「指摘がなくなるまでループ」し、最低 3 ラウンド実施する。

#### レビューループの仕組み

1. 4 つのレビュアーサブエージェントを**新規に**作成し、並列実行する
2. 各レビュアーの結果を収集する
3. Critical または Warning の指摘がある場合 → Phase 3（修正）に進み、修正後に再度 Phase 2 に戻る
4. 指摘がない場合でも、累計ラウンド数が 3 未満なら新しいサブエージェントで再レビューする
5. 累計 3 ラウンド以上かつ指摘なし → Phase 4 に進む

毎ラウンド新しいサブエージェントを作成する理由: 前のラウンドのコンテキストに引きずられず、フレッシュな目でレビューするため。

| レビュアー | 観点 |
|-----------|------|
| 機能レビュアー | 要件充足・ロジック正確性 |
| アーキテクチャレビュアー | 設計整合性・保守性 |
| セキュリティレビュアー | 脆弱性・安全性 |
| パフォーマンスレビュアー | N+1・ループコスト・データ量・再レンダリング等 |

各レビュアーへの指示:
```
<レビュアーサブエージェントに渡すプロンプトのテンプレート>
spec: <spec.md のパス>
レビュー対象: <変更されたファイルのリスト>
レビューラウンド: <現在のラウンド番号> / 最低3ラウンド
前回の指摘事項: <前ラウンドの指摘サマリ（初回は「なし」）>
```

### Phase 3: レビュー指摘の修正

レビューで指摘された問題をコーダーサブエージェントで修正する。
修正が必要な指摘をマージし、重複を排除してからタスクとして割り当てる。

修正完了後、Phase 2 に戻って再レビューする。

### Phase 4: QA（動作確認）

QA テスターサブエージェントが chrome-devtools MCP を使用してブラウザ上で動作確認を行う。
```

```
## オーケストレーション指示

### 実行フロー

```
Phase 1 (コーディング)
  ↓
Phase 2 (レビュー) ←──┐
  ↓                    │
  指摘あり? ───Yes──→ Phase 3 (修正) ──→ Phase 2 に戻る
  ↓ No
  3ラウンド以上? ──No──→ Phase 2 に戻る（新規サブエージェント）
  ↓ Yes
Phase 4 (QA)
  ↓
  問題あり? ───Yes──→ 修正 → Phase 2 に戻る
  ↓ No
Phase 5 (最終確認)
```

### ルール

- レビューは毎ラウンド新しいサブエージェントを作成して実行する
- レビューは最低 3 ラウンド実施する。指摘がなくなっても 3 ラウンド未満なら続行する
- Phase 4 で問題が見つかった場合は、修正して Phase 2 に戻る（レビューラウンドのカウントはリセット）
- レビュー + 修正のループが 5 回を超えた場合はユーザにエスカレーションする
```
