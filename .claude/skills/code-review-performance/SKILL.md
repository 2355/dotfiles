# パフォーマンスレビュー

実装にパフォーマンス上の問題がないかをレビューする。あなたはレビュアーであり、修正者ではない。ファイルは一切編集せず、指摘の報告だけを返す（修正は呼び出し元が行う）。

## 資料の取得

このレビューは会話履歴を持たないサブエージェントで実行される。実装時のやり取りに引きずられないための意図的な分離なので、判断材料は以下の手順で自分で集める。

1. **差分**: `$range` が指定されていれば `git diff $range` で取得する。未指定（空、または `$range` の文字列のまま残っている場合）は `git diff` を使い、未コミット差分がなければ `git diff HEAD~1` を見る。新規追加ファイルは `git diff` に現れないので `git status --porcelain` も確認し、未追跡ファイルは直接 Read する
2. **ブリーフ**: `$brief` にパスが渡されていれば Read で読む。変更ファイル一覧と設計上の決定事項が書かれている。未指定なら差分だけで判断する
3. **既存パターン**: 同種の処理が既存コードでどう書かれているか（eager loading、バッチ取得、キャッシュ層など）を確認する

## 観点

- DB アクセス: N+1 クエリ、不要なクエリの発行、インデックスを使えていないクエリ
- ループ処理: 不要なループのネスト、ループ内での重い処理（DB アクセス、外部 API 呼び出しなど）
- データ量: 大量データを一括でメモリに載せる処理、ページング・ストリーミング不足
- 非同期処理: 同期/非同期の使い分け、無駄な await の直列化、並列化できる処理が逐次になっていないか
- キャッシュ: 同一データの重複取得、キャッシュ可能な処理を毎回計算していないか
- フロントエンド: 不要な再レンダリング、重い処理によるメインスレッド占有、バンドルサイズ増加

## レビューの進め方

1. DB アクセスのある箇所を特定し、ループ内で発行されていないか（N+1）を確認する
2. 既存の N+1 回避パターン（eager loading、バッチ取得、JOIN など）を踏襲しているか確認する
3. 大量データを扱う箇所でページング・ストリーミングが使われているか確認する
4. フロント側の変更がある場合、再レンダリングや計算コストの増加がないか確認する

## 報告フォーマット

```markdown
## パフォーマンスレビュー結果

### チェックサマリ

| カテゴリ | 状態 |
|---------|------|
| DB アクセス（N+1 等） | OK / 要対応 / N/A |
| ループ処理 | OK / 要対応 |
| データ量 | OK / 要対応 / N/A |
| 非同期処理 | OK / 要対応 / N/A |
| キャッシュ | OK / 要対応 / N/A |
| フロントエンド | OK / 要対応 / N/A |

### 指摘事項

#### [Critical / Warning / Info] 指摘タイトル

- 対象: <ファイルパス:行番号>
- 内容: <何が問題か>
- 影響: <どの程度のパフォーマンス劣化が予想されるか>
- 提案: <どう修正すべきか>
```

## 判断基準

- Critical: 本番環境で深刻な劣化を引き起こす可能性が高い（N+1 で大量レコードを舐める等） → 修正必須
- Warning: パフォーマンス上の懸念がある → 修正推奨
- Info: より良い改善の提案 → 任意
