description: 指定日（省略時は今日）の Claude Code セッション記録（~/.claude/projects 配下の JSONL）を集め、作業内容と学びを抽出して日報（~/work/nippo/YYYY-MM-DD.md）の作業ログと「💡 学びと気づき」に書き起こす。学び候補はユーザに選ばせてから書き込む。「Claude とのセッションから学びを日報に書いて」「今日の学びを抽出して」「セッションの学びをまとめて」などと言われた場合にこのスキルを使用する。

---

指定日の Claude Code セッションから、日報に残す価値のある作業内容と学びを抽出し、ユーザの選択を経て日報に書き込む。

- 対象日: `$ARGUMENTS` に `YYYY-MM-DD` があればその日、なければ `date +%Y-%m-%d` の値
- 書き込み先: `~/work/nippo/<対象日>.md`
- コードレビュー、開発、調査、相談など、セッションの種類は問わない

## 手順

### 1. セッション記録を抽出する

スクリプトで、ユーザ発言（AskUserQuestion への回答を含む）と Claude のテキスト応答だけを抜き出す。生の JSONL は大半が tool_result で、直接読むとコンテキストを圧迫するため、JSONL を Read してはいけない。

```bash
~/.claude/skills/extract-learnings/scripts/extract.sh <対象日> <出力先>
```

- 出力先は、scratchpad ディレクトリがあれば `<scratchpad>/extract-learnings/<対象日>`、なければ省略する（一時ディレクトリが作られる）
- 標準出力の 1 行目は `OUT_DIR=<出力先>`。続く行は、セッションごとのファイル名・サイズ・当日のユーザ発言数・タイトル
- stderr に `skip:` が出たファイルは読み込めなかったもの。最後の報告でユーザに伝える
- スクリプトが自動で除外するもの:
  - 当日のユーザ発言がないセッション
  - 日報（`~/work/nippo`）を操作するセッション
  - このスキルを起動した地点より後のやりとり（同じセッションで、それより前に行った作業は残る）
- 1 件も出力されなければ「対象日のセッションはありません」と伝えて終了する

### 2. セッションを読んで候補を作る

出力された各 md を Read する。1 ファイルが大きく Read が失敗する場合は、offset / limit で分けて読む。合計が 150KB を超える場合は、セッションごとに Agent（general-purpose）へ読ませて候補を返させ、メインのコンテキストを守る。その場合も、この節の基準と出力形式をそのままプロンプトに含める。

md 内のタイトル（`title:`）は Claude Code が自動で付けたもので、内容とずれていることがある。参考にとどめ、見出しは中身から作る。

各セッションについて、次の形で候補を作り、手元に保持する。session id は手順 4 で使う。

```markdown
#### S<連番>: <session id>
作業ログ案:
- 時刻: HH:MM
- 要約: <20 文字程度>
- 本文: <1〜3 文>
学び候補:
1. <学び>
2. <学び>
```

**作業ログ（事実）**: そのセッションで何をしたかを書く。
- 時刻は、そのセッションの当日最初の `USER` 見出しの時刻を使う
- 要約は見出しに使うので、20 文字程度に収める
- PR・Jira キー・artifact の URL がセッションに出てきていれば、本文に含める
- 実際にしたこと・分かったこと・決まったことだけを書く。「〜は未決定」「〜は未着手」のように、起きなかったことは書かない。日報を後で読み返すときに必要なのは起きた事実で、未決着・未着手のものは次のセッションで改めて扱われるため。「〜を見送った」「〜しないと決めた」は決まったことなので書いてよい

**作業ログと学び候補に共通**: 日報はセッションを見ていない人（後日の自分を含む）が読むので、セッション内でしか通じない番号や略称を使わない。
- 使わないもの: 「案A」「論点3」「Q3」「R8-B1」「Phase 2」「①」のように、議論・grilling・レビューの中で振られた番号や記号、Claude やユーザがその場で作った略称、このスキル内の `S<連番>`
- 指す中身そのものを書く（例: 「案B を採用」ではなく「キャッシュを Redis に置く案を採用」）。要約の字数が足りないときも、番号に頼らず中身を短く言い換える
- 使ってよいかは、日報の読者がその名前だけで中身を検索・特定できるかで判断する。PR 番号・Jira キー・ファイル名・コード上の識別子は使ってよい。spec などのドキュメント内の項目番号は使わない

**学び候補**: 次のどちらかの形で書く。
- **教訓**: 別の場面でも使える教訓を書き、括弧で具体例を添える。形式は `<教訓>（例: <どの PR・ファイル・チケットで何があったか>）`
  - 例: `外部 API のレスポンスをモックするテストでは、モックの形を実レスポンスから作る。手書きのモックは型が通っても実際の形とずれることがある（例: PR #1234 の client.test.ts で、null になり得るフィールドを省いたモックにしていたため、本番でだけ落ちた）`
- **知見**: プロジェクト固有の仕様・規約・設計意図のように、教訓へ一般化しにくい事実は、無理に一般化せず 1〜2 文で事実として書く。末尾に出典（チケット・PR・ドキュメント）を括弧で添える

学びとして拾うもの:
- ユーザの質問で明らかになった、知らなかった仕様・挙動・設計意図
- ユーザが Claude の回答や実装の誤りを指摘し、正しい結論に落ち着いたもの
- デバッグで見つけた根本原因と、その切り分け方
- 設計判断とその理由（採用しなかった案があれば、その理由も）。AskUserQuestion への回答として記録されているものも含める
- レビューで「このコード・テストは良くない／不要」と結論が出た観点
- ツール・ワークフロー・Claude の使い方についての発見

拾わないもの:
- 進捗報告や作業手順の羅列だけのもの（作業ログに書く）
- 結論が出ていない論点、途中で覆された見解。判定は論点ごとに行い、セッション全体が未決着でも、その中で確定した事実は拾ってよい
  - やりとりが続いた場合は、最後の結論を採用する。Claude の回答にユーザが反論せず次の話題へ移った場合は、結論として扱ってよい
- Claude が推測で述べ、検証されていない部分。推測の部分は削って書く。学びの中心そのものが未検証で、それでも残す価値がある場合に限り、末尾に「（未検証）」を付ける
- 具体例の内容から外れるほど一般化した教訓。言い過ぎるくらいなら、適用範囲を絞った表現にする

複数のセッションで同じ学びが出た場合は、経緯が詳しいほうのセッションに 1 つだけ残す。候補が 1 つもないセッションは、作業ログだけでよい。

### 3. ユーザに候補を選ばせる

まず、手順 2 の候補をすべてテキストで提示する。そのうえで `AskUserQuestion` の multiSelect で、書き込む学びを選ばせる。

- question は、セッション単位で作る。header は `S1` のようなセッション番号にする
- options の label は学びを 30 文字程度に縮めたもの、description は学びの全文にする
- 1 つの question に入る options は 2〜4 個。候補が 5 個以上なら question を分け、1 個だけなら、ほかの 1 個だけのセッションと 1 つの question にまとめる（header は `S2+S4` のようにする）。それでも 1 個しかない場合は、その候補を label にした option と「書き込まない」の 2 択にする
- 1 回の呼び出しに入る question は 4 つまで。超える場合は呼び出しを分ける
- 何も選ばれなかった question の候補は、書き込まない
- 選択肢の「Other」に書かれた指示（文言の修正、作業ログの除外や修正など）に従う。作業ログについては質問を立てず、確認なしで書いてよい

### 4. 日報に書き込む

`~/work/nippo/<対象日>.md` を Read する。ファイルがなければ、`~/.claude/commands/nippo-add.md` の新規作成テンプレートと同じ構造で作る。ただし、次の 2 点は変える。
- タイトルの日付は、今日ではなく対象日にする
- 「初回記録」のエントリは作らない

**作業ログ**: `## 📝 作業ログ` セクションに、セッションごとに次の形式で追加する。

```markdown
### HH:MM - <要約>
<!-- claude-session: <session id> -->
<本文>

---
```

- 既存のエントリは `### HH:MM` の時刻順に並んでいるので、時刻順になる位置に差し込む
- 同じ session id のコメントを持つエントリがすでにあれば、同じ日に再実行したということなので、新しく追加せずに、そのエントリの要約と本文を今回の内容で置き換える

**学び**: `## 💡 学びと気づき` セクションの末尾に、選ばれた候補を `- ` の箇条書きで追加する。
- プレースホルダの「（随時追記）」が残っていれば、それを置き換える
- すでに同じ趣旨の箇条書きがあれば追加しない

書き込みが終わったら、追加・更新した内容をユーザに示す。commit と push は `nippo-finalize` の担当なので、このスキルでは行わない。
