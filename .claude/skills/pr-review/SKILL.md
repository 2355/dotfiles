# PR Review

組み込みの `/code-review` は指摘の中身は良いが、報告が「どれに注目すべきか」「どう直すか」を示さず、情報が表の外に散らばる。このスキルは `/code-review` をそのまま走らせ、出てきた指摘を **検証 → 重要度付け → 整形** してからユーザに渡す。

```
         ┌─▶ /code-review 実行 ──▶ 指摘を抽出 ──▶ 1 件ずつ独立検証 ──▶ 重要度付け・直し方 ─┐
開始 ────┤     (組み込み)          (場所を確定)     (サブエージェント)      (P0〜P3)           ├─▶ 報告
         └─▶ /pr-guide で解説ページ作成（PR が対象 かつ --no-guide なしのとき）────────────┘   (表 + カード + 解説リンク)
```

/code-review の結果は中間生成物。手順 4 の報告を出すまで、ユーザ向けのまとめは書かない。

## 1. /code-review と /pr-guide を並列に始める

### 1-1. 起動前に引数を解釈する

何かを起動する前に、次を決める。途中で中止すると、先に起動したものだけが走り続けてしまうため。

- `ultra` がある: 本スキルでは扱わない。素の `/code-review ultra` を使うよう案内して終える（何も起動しない）。ultra はクラウドで多数のエージェントが動く別系統のレビューで、本スキルの検証と役割が重なり、費用も大きいため
- 対象が PR か: PR 番号か PR の URL なら PR。ブランチ・未コミットの差分・パスは PR ではない（そのブランチに PR があっても PR としては扱わない）
- 解説ページを作るか: 対象が PR で、かつ `--no-guide` が無いときだけ作る。`/pr-guide` は PR の URL を入力に取るため
- 解説ページを作る場合で PR 番号だけを渡されたら、`gh pr view <番号> --json url -q .url` で URL にしておく

### 1-2. 同じターンで両方を起動する

解説ページを作る場合は、次の 2 つを同じターンで起動する。作らない場合は code-review だけを起動する。

- **/pr-guide**: Agent ツールで `subagent_type: general-purpose` のサブエージェントを 1 つ起動し、次のように頼む
  - Skill ツールで `pr-guide` を引数 `<PR の URL>` で実行する
  - 公開した artifact の URL を返す
  - 途中でユーザに尋ねる必要が出たら、尋ねずに理由を添えて失敗として返す（バックグラウンドではユーザに尋ねられないため）
  - メインのスレッドで直接呼ばないのは、解説ページ作りで読む資料がレビューの文脈を圧迫しないようにするため
- **/code-review**: Skill ツールで組み込みの `code-review` を呼ぶ。引数はユーザから受け取ったものを渡すが、次は扱いを変える
  - `--no-guide`: 本スキル用の引数なので渡さない
  - `--comment` / `--fix` / `--post`: 外して実行する。検証前の指摘が PR に書かれたりコードに適用されたりすると、棄却すべき指摘まで外に出るため。外したことは手順 4 の末尾で扱う

### 1-3. 完了を待ち合わせる

どちらもバックグラウンドで動き、終わると完了通知が来る。ポーリングはせず、通知を待つ。通知が届く順番は決まっていない。

```
起動（guide, review）─▶ ターン終了
  ├─ guide の完了通知  → artifact の URL を控える。ユーザ向けには何も書かない
  └─ review の完了通知 → 手順 2・3 へ
手順 3 が完了 かつ guide が完了 → 手順 4
```

- guide のサブエージェントが URL を返さずに終わった場合（エラー、権限の拒否、ユーザへの質問が必要など）は失敗とみなす。手順 4 の前に、メインのスレッドで Skill ツールの `pr-guide` を実行して作り直す
- 組み込みの code-review は報告方法（ReportFindings ツールでの報告など）を指示してくる。指摘を一覧にするためにそれに従ってよいが、それはレビューの中間結果であり、作業の完了ではない。組み込み側のまとめ文はユーザ向けに書かず、そのまま手順 2 に進む

## 2. 指摘を抽出し、場所を確定する

`/code-review` の結果から各指摘について次を取り出す:

- 場所: リポジトリルートからのパス + 行番号。複数箇所なら全部
- 主張: 何が問題か
- 起きること: どんな条件で何が起きるか

組み込みの出力はファイル名だけ（`useCreditCardForm.ts:175`）のことがあるので、`git ls-files` などでフルパスに直す。行番号は **レビュー対象の変更後（PR なら head 側）の行** に揃える。行が分からない指摘は、手順 3 で特定させる。

PR が対象なら、手順 3 の前に `git fetch origin pull/<番号>/head` で head をローカルに取ってきて、その sha を控える（作業ツリーが PR のブランチとは限らず、head がローカルに無いとファイルを読めないため）。並行して動く pr-guide も fetch するので、lock のエラーで失敗したら少し待ってからやり直す。

## 3. 指摘を独立に検証する

`/code-review` の指摘には偽陽性や、深刻さの見積もり違いが混ざる。ユーザが「どれを直すか」を判断する材料なので、出す前に裏を取る。

各指摘につき 1 つ、Agent ツールでサブエージェントを **並列に** 起動する（指摘が 10 件を超える場合は、同じファイル・同じ原因の指摘を 1 つのエージェントにまとめてよい）。プロンプトには以下を含める:

- コードの読み方
  - PR: `gh pr diff <番号>` と、変更後のファイルを `git show <head の sha>:<path>` で読むこと
  - ローカル差分・ブランチ: ベースのコミットと、`git diff <base>` で差分を見ること
  - パス指定: そのパスを作業ツリーで読むこと
- 指摘の場所・主張・起きること（手順 2 で抽出したもの）
- 役割: 「この指摘を **反証しにいく** 独立レビュアー」。指摘の言い分を鵜呑みにせず、実際のコード・呼び出し元・型・既存のガードを読んで成立するかを確かめる。ファイルは変更しない
- 返してほしいもの:
  - 判定: `妥当` / `一部妥当`（条件や影響範囲が主張より狭い）/ `棄却`（成立しない）
  - 場所: 変更後の行での `path:line`。該当行が無い指摘（「テストが無い」など）は、追加・変更すべき位置の `path:line`
  - 根拠: 確認したコードの `path:line` と、そこから何が言えるか
  - 未確認の点: コードだけでは確かめられなかったこと（実行時の表示、外部 API の挙動など）。推測で埋めず、ここに入れる
  - 発生条件と影響: 誰に・どのくらいの頻度で・何が起きるか
  - 直し方: どのファイルのどこをどう変えるか。案が複数あれば推奨を先頭に
  - 関連: 他の指摘と同じ原因なら、その旨

判定結果の行き先:

| 判定 | 未確認の点 | 行き先 | 検証欄 |
| --- | --- | --- | --- |
| 妥当 / 一部妥当 | なし | 本表 + カード | ✅ 確認済み |
| 妥当 / 一部妥当 | あり | 本表 + カード | ⚠️ 一部未確認 |
| 成立も否定もできない | — | 本表 + カード | ⚠️ 一部未確認 |
| 棄却 | — | 末尾の「棄却した指摘」 | — |

`一部妥当` は、カードの「問題」「起きること」を狭まった条件で書き、その条件で重要度を付ける。

## 4. 重要度を付けて報告する

### 重要度の基準

重要度は「不具合 / 設計」というカテゴリではなく、**マージした場合に誰がどれだけ困るか** で決める。設計の指摘でも放置すると事故につながるなら上げ、不具合でも発生条件が極めて狭く影響が軽いなら下げる。

| 重要度 | 表記 | 意味 | 目安 |
| --- | --- | --- | --- |
| P0 | 🔴 P0 | マージ不可 | 主要な画面・機能が使えなくなる、データ破損、お金や個人情報の誤り、悪用できる脆弱性 |
| P1 | 🟠 P1 | マージ前に直す | 一部のユーザ・条件で誤動作する、ユーザに誤解を与える表示、目に見える性能劣化 |
| P2 | 🟡 P2 | 直すべきだが後続でも可 | まれな条件での誤動作、軽い性能のムダ、保守性を明確に損なう重複や構造 |
| P3 | ⚪ P3 | 任意の改善 | 命名・コメント・テストやモックの整理など、動作に影響しないもの |

### 出力形式

以下の構成で出す。この外（表の前後の段落、「確度」「補足」などの別セクション）に指摘の情報を書かない。共通の原因も確度も、それぞれのカードの中に書く。1 件の指摘を理解するのに複数の場所を読ませないため。

````markdown
## <対象> のレビュー結果（<effort>）

PR の解説: <pr-guide の artifact URL>

🔴 P0: <n> 件 / 🟠 P1: <n> 件 / 🟡 P2: <n> 件 / ⚪ P3: <n> 件（棄却 <n> 件）

| 重要度 | # | 一言 | 検証 |
| --- | --- | --- | --- |
| 🔴 P0 | 1 | pricing が non-null になり、支払いページ全体が落ちる | ✅ |
| 🟠 P1 | 2 | 予約中のプラン変更の金額が今から課金されるように表示される | ⚠️ |

### #1 🔴 P0 `app/mypage/payment/query.ts:17` — pricing が non-null になり、支払いページ全体が落ちる

- **問題**: <何が問題か>
- **起きること**: <条件> → <結果>。<影響を受けるユーザ>
- **直し方**: <どのファイルのどこをどう変えるか>
- **検証**: ✅ 確認済み — <根拠。確認した `path:line`>
- **関連**: #2, #3 と同じ原因（<原因>）

### #2 🟠 P1 ...

## 棄却した指摘

- `path:line` <元の指摘の一言> — <棄却理由と根拠 `path:line`>

---
どれを直すか指示をもらえれば対応します。
````

各部分のルール:

- **見出し**: `<対象>` は `PR #8802`、`ブランチ feature/x`、`未コミットの差分` など。effort を指定していなければ `（<effort>）` を省く
- **PR の解説**: 解説ページを作ったときだけ、artifact の URL を書く。pr-guide が返すまとめ文は載せない（解説はページ側で読めるため）。作らなかったときは行ごと省く。メインのスレッドでの作り直しも失敗した場合は「解説ページの作成に失敗（理由）」と書く
- **重要度の表記**: 件数の行・表・カード見出しのすべてで、基準表の「表記」列（色の丸 + P 番号）を使う。ターミナルの Markdown では文字色を付けられないので、色の丸で重要度を見分けられるようにするため
- **並び順**: 重要度順。同じ重要度の中では影響の大きい順。`#` は並べ替えた後の順に 1 から振り直す
- **場所**: 手順 2 で揃えた `path:line` をカードの見出しに書く。サマリ表には書かない（フルパスで表が横に広がり、一覧性が落ちるため）
- **一言**: 「何が起きるか」を 40 字程度で。原因のコード名より、結果を書く
- **検証**: 手順 3 の表に従う。⚠️ のときは何が未確認かを書く
- **直し方**: 「〜を検討」で終わらせず、変更するファイルと変更内容を書く。共通原因でまとめて直せる場合も、各カードに 1 行の要約を書く（例: 「#1 と同じ修正（Apple Pay 用の取得をクリック時の遅延取得に移す）で解消」）。カード 1 枚で完結させるため
- **関連**: 無ければ行ごと省く
- **棄却した指摘**: 無ければセクションごと省く
- **外したフラグ**: 手順 1 で `--fix` を外した場合は「検証済みの指摘のうちどれを直すか」を、`--comment` / `--post` を外した場合は「検証済みの指摘を `gh api` で PR にインラインコメントするか」を、最後の一文の代わりに尋ねる。組み込みをフラグ付きで再実行するとレビューからやり直しになり、検証していない指摘が適用・投稿されるため、再実行はしない
