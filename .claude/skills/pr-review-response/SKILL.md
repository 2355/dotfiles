$ARGUMENTS を元に PR のレビューコメントに対応してください。

## 前提

- PR を作成しているのは原則ユーザ自身。レビューに対する対応者として動く。
- 副作用が大きい操作（コミット、プッシュ、GitHub への返信）は必ずユーザの確認を取ってから実行する。

## 手順

### 1. 対象 PR の特定

- $ARGUMENTS が PR URL または PR 番号として与えられていればそれを使う。
- 与えられていなければ `gh pr view --json number,url,baseRefName,headRefName` で現在のブランチに紐づく PR を取得する。
- PR が見つからない場合はユーザにエラー報告して終了。

### 2. レビューコメントの取得

以下の API を組み合わせて取得する。レビューコメントには複数の種類があるため、漏れがないように両方確認する。

- **line-level レビューコメント**（最も一般的）:
  - `gh api repos/{owner}/{repo}/pulls/{pr_number}/comments`
  - Copilot / Codex などの bot レビュー、PR 上の特定行に紐付くコメントはここ
- **issue 形式の PR コメント**（PR 全体への汎用コメント）:
  - `gh api repos/{owner}/{repo}/issues/{pr_number}/comments`
  - こちらは「PR 全体への意見」だが、レビュアーがここに技術的指摘を残す場合もある
- **レビュー本体のサマリ**:
  - `gh api repos/{owner}/{repo}/pulls/{pr_number}/reviews`
  - 各レビューに本文がある場合があるので一読する

取得時の注意：

- すでにユーザ自身が返信済みのコメント（in_reply_to で繋がっているスレッド末尾が自分の発言）は対応済みとみなしてスキップ候補とする。
- 「Outdated」（diff_hunk が古い）コメントもユーザに提示して対応要否を確認する。

### 3. コメントの整理と方針提示

各コメントについて以下を整理し、ユーザに対応方針を提示する。

- コメント ID
- 投稿者（Copilot / 人間）
- 該当ファイル・行
- 指摘内容の要約
- **提案する対応方針**:
  - 対応する（修正案を簡潔に書く）
  - 対応しない（理由を書く。例: スコープ外、現状で問題ない、別 PR で扱う）
  - 判断が割れそうなものはユーザに確認

**対応の対象はコードだけではない**ことに注意する。Copilot などのレビューは PR 本文（description）の記述に対しても指摘することがあり、その場合はコミット不要で `gh pr edit {pr} --body-file <tmpfile>` だけで完結する。コメント内容から「何を直すべきか」を毎回判断し、「常にコード修正＋コミット」を前提に進めない。

CLAUDE.md の「ユーザの指摘を無条件に受け入れない」を踏まえ、Copilot の指摘も「無条件に正しい」と扱わずに妥当性を評価する。明らかに見当違いの指摘は「対応不要」とし、その理由を返信に書く方針で提案する。

提示後、ユーザの承認を得る。AskUserQuestion などを使って方針確定までの往復を減らす。

### 4. コード修正

承認された方針に従い、修正を行う。

- コードの変更は最小限。指摘されていない箇所を「ついで」で変更しない。
- 修正後はリポジトリのテスト・lint を必ず実行（プロジェクトの CLAUDE.md に従う）。
- テストが失敗したら修正し直す。確認なしで指摘内容を変えない。

### 5. コミット

**デフォルトは「指摘ごとにコミット分割」**。

- 1 コメント = 1 コミットを基本とする。レビュアーが「どの指摘がどのコミットで解決されたか」を辿りやすい。
- 関連の強い複数指摘をまとめたい場合や、まとめる方が自然な場合はユーザに確認してから判断する。
- コミットメッセージはプロジェクトの規約（CLAUDE.md があれば従う）に合わせる。本文に「Copilot 指摘 #N への対応」など、由来が分かる情報を添えると後追いしやすい。

すべての修正をいったん作業ツリーに入れた状態から、指摘ごとにコミットを分けたいときは：

1. `git stash` で全変更を退避
2. 各指摘の修正を順に Edit ツールで再適用
3. 修正ごとに `git add` → テスト確認 → `git commit`
4. `git stash drop` で退避を破棄

の手順が安全。`git add -p` での分割もあり得るが、ファイル間の対応関係が複雑な場合は再適用方式の方がミスが少ない。

コミット前にユーザにコミットメッセージ案を提示して確認する（CLAUDE.md の「自動的にコミットやプッシュを行わない」に従う）。

### 6. プッシュ

`git push` で origin に反映。プッシュ前にユーザの確認を取る。

### 7. 各コメントへの返信

`git rev-parse <short-sha>` でフル SHA を取得し、コミット URL を組み立てた上で各コメントに返信する。

```
gh api repos/{owner}/{repo}/pulls/{pr_number}/comments \
  -f body="https://github.com/{owner}/{repo}/pull/{pr_number}/commits/{full_sha} で対応しました" \
  -F in_reply_to=<comment_id>
```

返信フォーマットは以下を基本とする：

- **コード修正で対応した場合**: `{commit_url} で対応しました`
- **複数コミットで対応した場合**: 各 URL を箇条書きで列挙し、最後に「で対応しました」
- **PR 本文修正で対応した場合**: `PR 本文の該当箇所を〜に修正しました` のように、対応の実体を簡潔に伝える
- **対応しなかった場合**: 「対応しません。理由：〜」と理由を書く

定型 (`{commit_url} で対応しました`) でない返信を返す場合は、投稿前に文言をユーザに見せて確認を取る。GitHub への投稿は取り消しが面倒なため、一手前で間違いを防いだほうが安い。

`issues/{pr_number}/comments` 由来のコメント（line に紐付かない PR 全体コメント）は `in_reply_to` 機構がない場合があるため、その場合は新規 comment として投稿するか、PR review として返す。

### 8. 完了報告

ユーザに以下を報告する：

- 対応したコメント数 / 対応しなかったコメント数
- 作成したコミットの一覧（SHA と一行サマリ）
- プッシュ先ブランチ
- 返信を投稿したコメント ID と URL

## 注意事項

- **コメントを取り違えない**: in_reply_to に渡す ID は元コメント（Copilot などが書いたコメント）の ID であって、レビュー本体の ID ではない。`/pulls/{pr}/comments` で取れる各要素の `id` を使う。
- **複数 SHA の URL は省略形（短縮 SHA）でなく完全 SHA を使う**: 短縮 SHA だと将来 git の参照解決で問題になり得る。
- **`gh api` の `-F` と `-f` の使い分け**: 数値は `-F`（生値）、文字列は `-f`（クォート）。`in_reply_to` は数値なので `-F`。
- **gh api の出力が JSON で長い場合**: パイプして `python3 -c "import sys,json; ..."` などで必要なフィールドだけ取り出すと取り回しがよい。
