$ARGUMENTS の PR をレビューし、マージ可否を判断する。

## 手順

### 1. PR 情報を収集する

- `gh pr view` で PR のタイトル、本文、変更ファイルを取得する
- 変更ファイルの diff を確認し、対象パッケージとバージョン変更を特定する

### 2. コードベースでの使用状況を調査する

- 対象パッケージが import/require されている箇所を Grep で検索する
- gem の場合は Gemfile での指定と、コードベース内で使われているモジュール・クラスを確認する
- 使用箇所の数と使われ方の概要を把握する

### 3. バージョン間の変更内容を確認する

- PR 本文に CHANGELOG やリリースノートが記載されていれば、それを読む
- 記載がなければ、Web 検索で CHANGELOG を確認する
- バージョンごとに変更内容を整理する（例: v2.12.0, v2.13.0 のように個別に記載する）
- BREAKING CHANGE がある場合は、該当バージョンに **[BREAKING]** を明記する
- 特に以下に注目する：
  - BREAKING CHANGE の有無
  - 非推奨になった API
  - セキュリティ修正

### 4. リスクを評価する

以下の観点でリスクを判定する：

- **バージョン変更の大きさ**: メジャー > マイナー > パッチ
- **BREAKING CHANGE の有無**: ある場合は、コードベースの使用箇所が影響を受けるか確認する
- **使用範囲の広さ**: 広く使われているほどリスクが高い
- **テストカバレッジ**: 影響を受けるコードパスに対するテストが存在するか確認する

### 5. 注意事項

- 不明点は憶測で判断せず、PR の記載情報やソースコードを確認すること
- 「CI パス＝マージ安全」と想定しないこと。影響を受けるコードパスに対する具体的なテストカバレッジが存在するか必ず検証し、関連テストが存在しない場合は明示的にその旨を述べる

## 出力フォーマット

GitHub PR へのコメント用に、以下のテンプレートに従って markdown で出力する。
セクション構成と見出しは必ずこのテンプレート通りにする。

```markdown
## {パッケージ名} {旧バージョン} → {新バージョン}

### コードベースでの使用状況

- 使用箇所の一覧と概要

### バージョン間の変更内容

#### v{X.Y.Z}

- **[BREAKING]** {破壊的変更がある場合は先頭に記載}
- 主要な変更点

#### v{A.B.C}

- 主要な変更点

### リスク評価

| 観点             | 評価                   |
| ---------------- | ---------------------- |
| バージョン変更   | patch / minor / major  |
| BREAKING CHANGE  | あり / なし            |
| 使用範囲         | 広い / 限定的 / 未使用 |
| テストカバレッジ | あり / 一部あり / なし |

{リスクに関する補足説明}

### 判定

**{✅ マージ可 / ⚠️ 条件付きマージ可 / ❌ マージ不可}**

{判定理由}
```
